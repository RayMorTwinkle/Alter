# ADR-0014 记忆：常驻索引 + 条目，按累积量整理

- 状态：已接受
- 日期：2026-11-23
- 修订：ADR-0005（记忆部分）

## 背景

现在的记忆是一张扁平表（偏好 / 目标 / 事实），字面子串搜索，只有主会话主动调用 `memory_save` 才写入。主会话没有"我对这个用户的整体了解"，从互动和用户自己的发言里看出来的偏好也记不下来。

用户画像是 Alter 主动性的基础：巡检找事、语气、该不该打扰，都取决于它。PrefEval 基准显示，偏好不常驻上下文时，对话十轮后多数模型遵循偏好的准确率低于 10%。HaluMem 显示记忆系统主要错在抽取和更新环节，便宜模型上越复杂越容易错。所以方案要**常驻、简单、可编辑**。

## 决策

**一、结构照 Claude Code 的记忆：索引 + 条目。**

- **索引**：每条记忆一行（标题 + 一句提示），放进主会话的**系统提示**（与 Claude Code 在会话开始时加载 MEMORY.md 相同）。系统提示是固定前缀，之后每轮都命中提示缓存，按缓存读计费（约正常输入的十分之一）。索引变化时**不改系统提示**（会让缓存失效），而是在下一次唤醒的输入里附一行"记忆更新：新增 / 修改 / 删除了哪些条目"；上下文压缩时再把最新索引整份放回系统提示。
- **条目**：标题、类型、正文（内容 + 为什么 / 怎么用）、来源、创建与更新时间。主会话用 `memory_read` 按需打开。
- 类型四种：**用户**（身份、兴趣、说话风格、作息——即画像）、**偏好**（对 Alter 做事方式的要求）、**目标**（可带期限，沿用现有目标逻辑）、**参考**（账号、地址、常用资源）。
- 条目可以标 **"猜的"**：整理时推测、用户没明说过的内容。回访时拿来问，确认后去掉标记，否定就删除。
- 索引超过上限（约 2000 字）时，下次整理必须合并相近条目。

**二、写入时机。**

- **当场写**：用户明说"记住"、纠正 Alter、表达明确偏好时，主会话立即写。
- **累积整理**：距上次整理累计 200–300 轮对话，且用户空闲 30 分钟时，后台整理一次。用户用得少就很久才整理一次，不空耗。
- 整理时对每条候选记忆，先检索最相近的条目，只能选：新增 / 修改 / 取代 / 不动（借鉴 mem0）。取代时旧条目保留在历史里，不直接删除。

**三、整理读什么：只看用户自己说的。**

- 用户与 Alter 的对话。
- 各消息来源中**用户本人发出**的内容：寄出的邮件、在飞书和社交平台上的发言、收藏与点赞。
- **别人发给用户的内容不用于推断画像。** 注入攻击来自他人写的内容，按作者过滤是最直接的防线。

**四、可见、可改、可撤销。**

- Web "记忆"页显示索引与每条条目，可直接编辑、删除、去掉"猜的"标记。
- 每次整理的改动记成一条变更（新增 / 修改 / 取代了哪些条目），可以在 Web 上撤销。
- 条目的来源写实际的消息 ID 或"整理于某日"，不另建证据层。

**五、检索。** 字面匹配换成 SQLite FTS5 全文检索。条目多到不够用时再考虑向量检索。

## 备选方案

- **画像文档 + 证据层 + 待确认清单**：概念多、证据没有实体，用户否决。
- **向量库 / 知识图谱（mem0、Zep）**：单用户条目量小，基准上优势不明显（LoCoMo 上全量上下文 72.9，最好的记忆系统 68.4），维护成本高。
- **每晚固定反思**：不用时空耗，素材少时会记下无意义的东西，改为累积触发。

## 后果

- 正面：主会话总带着对用户的了解；记忆是人看得懂的文字，用户可以直接纠正。
- 负面：整理依赖模型判断，可能记错；靠"猜的"标记、回访确认、变更可撤销兜底。
- 迁移：现有记忆按类型转为条目，标题取首句。
