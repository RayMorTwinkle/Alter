# ADR-0020 近况报告：每晚检查，至少两个任务才发；摘要消息先浓缩

- 状态：已接受
- 日期：2026-11-24
- 修订：ADR-0012 第三次修订（近况报告的频率部分）
- 关联：ADR-0017（回访，已暂停）

## 背景

原来的近况报告按最近 7 天活跃天数决定间隔（每 1/2/3 天），再乘上回访问卷答出的倍数；只要有一条摘要消息或一个完成的任务就发。问题：

- 问卷问"你想多久收一次"，和让用户自己设置没有区别。
- 只完成一件事也发一份报告，没什么可说的。
- 摘要消息含金量低，原样塞给主会话，而且缓冲区按 2400 字截断，旧消息会被悄悄丢掉。

## 决策

### 一、什么时候发

- 每天晚上的报告时刻检查一次（沿用活动时段内的晚间时刻）。
- 上次报告以来**完成的任务不少于 2 个**才发；摘要消息不计数。
- 不够就不发，游标不前进，留到第二天晚上继续累计。
- 7 天没有互动仍然暂停。
- 去掉按活跃天数的自适应间隔和问卷倍数。

"该不该发"由代码决定，规则可预测、可测试；"怎么说"交给主会话。

### 二、摘要消息先浓缩

- 发报告时，从通知存储取出上次报告以来的全部摘要级消息（不再用截断的缓冲区）。
- 任务模型做一次普通调用（无工具），略去低价值信息、合并相关消息，每句末尾附来源 ID，例如 `- GitHub 上两个仓库有新版本 [n_12, n_15]`。输入里不存在的 ID 会被剔除；调用失败或超时退回原始行。
- 主会话拿到浓缩后的摘要，需要时用只读工具 `digest_source` 按 ID 查原消息，不需要审批。

## 后果

- 正面：报告更少但每份都有内容；摘要消息不再被截断丢失；主会话能追溯来源。
- 负面：任务少的时期，摘要消息可能多日不推送；它们在网页通知栏里一直可见。每份报告多一次任务模型调用。
