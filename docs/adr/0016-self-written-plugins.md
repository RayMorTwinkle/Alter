# ADR-0016 Alter 自己写插件

- 状态：已接受
- 日期：2026-11-23
- 关联：ADR-0011（审批模型）、ADR-0013（插件三要素）、#72（消息来源）

## 背景

用户希望在自己允许的前提下，Alter 能编写插件来扩展自己：新的能力、新的消息来源，或两者都有。消息来源只是插件可以提供的一种东西，所以要做的是通用的"自写插件"，而不是单独的"模型写消息来源"。

调研（私有仓库 research/2026-11-23-self-extending-plugins.md）中三条有实证的结论决定了边界：

1. Node 官方明确说明 `--permission` 不是对抗恶意代码的安全边界；`isolated-vm` 在 2026 年 8 月仍有访客可触达的内存破坏漏洞。语言层隔离不够，需要操作系统层隔离。
2. 2025 年 `postmark-mcp` 的恶意版本在正常发信的同时暗中密送攻击者，功能测试全部能过。审查代码和跑测试不能证明没有额外副作用，对外动作必须经过可信的转发层。
3. 模型生成代码中幻觉包名的比例，商业模型约 5%、开源模型约 22%（USENIX Security 2025）；2025 年 Shai-Hulud 感染了 500 多个 npm 包。

## 决策

### 一、插件 = 清单 + 代码

清单 `alter-plugin.json` 是用户审批的对象，代码只实现清单写明的东西。清单包含：

| 字段 | 说明 |
|---|---|
| 工具 | 名称、输入输出结构、副作用等级（read / write-local / external-send / irreversible） |
| 消息来源 | 名称、拉取方式与最短间隔 |
| 网络 | 每条规则：域名、允许的方法、路径前缀 |
| 密钥 | 名称和用途，值由用户在设置页填写 |
| 借用能力 | 需要调用的已有工具，例如浏览器 |
| 资源 | 内存、单次超时、私有存储上限 |

### 二、运行：独立进程 + 系统沙箱，插件不碰网络

- 每个插件在独立的 Node 进程中运行，外面套一层 macOS Seatbelt（`sandbox-exec`）。默认禁止一切；只允许读取自己的代码目录，并通过管道和 Alter 通信。OpenAI Codex 在 macOS 上采用的就是这种做法。Seatbelt 已被 Apple 标为弃用，所以策略生成要封装成可替换模块，并配上逃逸回归测试。
- **插件不能自己联网。** 它通过 `alter.http.request()` 请 Alter 代发请求，Alter 先按清单校验，再真正发出。校验依次检查：只允许 HTTPS，域名精确匹配，解析出的 IP 不能是内网或回环地址，连接固定到已验证的 IP，方法和路径要符合规则，重定向逐跳重新校验，并限制大小和频率。
- **只读工具只能发不带请求体的 GET。** 这条由转发层用代码强制，不靠模型自觉。查询参数中不能出现带污点或密钥级的数据。
- 密钥不进入插件进程。插件只能指明"用密钥 X 填 Authorization 头"，由 Alter 在转发时填入。
- 插件的私有状态通过 Alter 提供的键值接口读写，插件拿不到实际文件路径。
- 借用已有能力等同于调用那个工具，照常经过 broker、污点标记和审批。

### 三、Alter 写插件的流程

1. **提出。** 只有用户在渠道里说的话，或者主会话自己的判断，才能发起"写插件"。消息来源、网页、邮件中的内容可以让 Alter 意识到缺什么能力，但不能视为用户的授权。开工前必须先问用户并得到同意。
2. **先找现成的。** 已有插件或模板（RSS / JSON / GitHub）能做到的，就不写新插件。
3. **编写。** 派一个任务，在独立的构建目录中按插件模板编写，同时写测试和离线替身数据。构建环境同样运行在沙箱里，拿不到用户密钥和 Alter 数据库。
4. **验收。** 验收由 Alter 执行，不由写代码的模型自己说了算，分四层：
   - L1 清单与装载；
   - L2 功能，用离线替身；
   - L3 安全负例，由 Alter 内置一套模型改不了的测试，包括越权域名、POST、重定向到内网、直接 socket、读其他文件、超时；
   - L4 真实试拉一次，样例给用户看。
5. **安装审批。** 卡片用白话写清能做什么、能连哪些网站和路径、要哪些密钥、**不能做什么**，并附上测试结果（由 Alter 生成，不由模型自述）和完整代码链接。必须由用户亲自点批准：审批模型不能代批，也不设超时。批准的对象是代码包的 SHA-256；安装和每次启动时都校验哈希。
6. **运行与熔断。** 初始阈值如下，之后用数据校准：
   - 连续失败 5 次：暂停并通知用户；
   - 出现一次越权网络请求：立即终止并隔离插件；
   - 消息来源产生事件过多：限流合并；
   - 返回结构连续 3 次对不上：暂停。
7. **升级。** 新版本重新走验收和审批。卡片显示与旧版的差异。权限扩大时醒目标出，包括新增工具、新增 external-send、新增域名或路径。旧版本保留，可以一键回滚。回滚同时恢复代码、清单、状态和消息来源的进度。

### 四、永远不给插件的东西

安装、升级或删除插件；修改 broker、清单校验器、审批策略；读取主数据库、Keychain、`.env`、用户文件；执行 shell、子进程、原生模块；修改自己的批准记录。插件最多只能产生一个"建议再写一个插件"的事件，由主会话按第三节的流程处理。

### 五、依赖

第一版插件不能引入 npm 包，只能使用 Node 标准库和 Alter 插件 SDK（HTTP 转发、键值存储、RSS/HTML 解析、日志）。确实常用的解析器，由开发者审核后放进 SDK。以后如果放开，必须同时满足：在注册表核实包确实存在，锁文件带完整性摘要，使用 `npm ci --ignore-scripts`，在无密钥的构建沙箱中安装，并经过用户单独审批。

### 六、分阶段

1. **框架。** 清单、独立进程、Seatbelt、HTTP 转发、键值存储、安装审批卡、哈希、版本与回滚、熔断。把 #72 的三种模板改写成这种插件，以此验证框架。
2. **自写。** 插件模板与 SDK 文档、编写任务、四层验收、试拉、审批页面。
3. **首个真实案例。** 小红书（借用浏览器、只读、低频拉取）。

## 不做

- 插件自动安装其他插件；无人批准的自动升级。
- 自研 TLS 中间人代理：由 Alter 代发请求已经能看到完整的请求内容。
- 每个插件一台虚拟机：只读类插件用不着，需要复杂依赖的插件以后再考虑 Lima。
- 不可逆操作的自动执行。

## 后果

- 插件写法受限，只能使用 SDK 和转发接口。好处是用户审批的内容和实际行为能对上。
- 每个自写插件都留下数据：缺什么能力、生成是否成功、修复轮数、验收失败的原因、用户拒绝的原因、沙箱拦截次数、上线后的复用次数。这些数据进统计页，并据此校准阈值。
- 安全负例测试和转发层由开发者维护，是整个机制的信任根，改动需要单独评审。
