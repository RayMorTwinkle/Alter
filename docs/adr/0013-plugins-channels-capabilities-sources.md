# ADR-0013 插件提供三种东西：渠道、能力、消息来源

- 状态：已接受
- 日期：2026-11-23
- 修订：ADR-0003（用词）

## 背景

ADR-0003 用 Surface / Connector 区分"用户对 Alter 说话的地方"和"Alter 代用户操作的账号"。飞书插件同时提供机器人、用户账号工具和收消息，出现了"收到飞书消息算不算插件""能力和消息来源有重合"的困惑。产品化后，这些概念会出现在 Web 设置页上，需要普通用户也能看懂的说法。

## 决策

**插件是安装和开关的单位。** 一个插件可以提供下面三种东西中的一种或多种：

| 插件提供 | 是什么 | 消息算什么 | 例子 |
|---|---|---|---|
| 渠道 | 用户和 Alter 说话的地方 | **指令** | Web（内置）、飞书机器人 |
| 能力 | Alter 主动调用的工具 | 结果是数据 | 发邮件、操作浏览器、读写飞书消息 |
| 消息来源 | 外面发生的事推进来 | **数据**，先分诊，绝不当指令 | 新邮件、他人发到用户飞书账号的消息 |

**能力和消息来源按"谁发起"区分。** Alter 主动去拿的是能力（"看看我最近的飞书消息"）；外面主动推进来的是消息来源（来了新消息就触发）。同一个接口可以两者都提供，例如飞书消息既可以被主动读取，也会推送新消息。

**飞书插件提供全部三种：** 机器人是渠道，读写用户消息是能力，他人发给用户的消息是消息来源。Web 是内置渠道。以后的微信、QQ 照此组织。

**Web 设置页按"插件 → 提供了哪些渠道、能力、消息来源"展示**，每项显示连接状态，配置也在这里完成（例如填写飞书 App ID 与 Secret），不要求用户编辑 `.env`。

## 备选方案

- **保留 Surface / Connector 两分法**：对开发者清楚，但用户看不懂，而且无法表达"消息来源"。
- **把消息来源并入能力**：消息来源是被动的，不经过调用，安全规则也不同（只分诊、不执行），并入后反而模糊。

## 后果

- 代码中的 `AlterSurface` 对应渠道，插件工具对应能力，`host.emit` 对应消息来源，概念一一对应，可逐步重命名。
- 渠道里的消息是指令，消息来源里的消息是数据，这条安全边界在产品界面上也变得明确。
