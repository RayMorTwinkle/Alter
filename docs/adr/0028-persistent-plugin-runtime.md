# ADR-0028 外部插件复用常驻并发进程

- 状态：已接受
- 日期：2026-11-26
- 关联：[ADR-0016](0016-self-written-plugins.md)、[#168](https://github.com/RayMorTwinkle/Alter/issues/168)、[#170](https://github.com/RayMorTwinkle/Alter/issues/170)

## 背景

ADR-0016 修订后，受用户批准的插件可以执行命令、直接联网，也可以维护设备会话。原运行时每次调用都重建 Node 进程。拉取消息期间，整个插件被占用，工具调用会收到 `Plugin is busy`。子进程只继承少量环境变量，声明的密钥又会被剔除，使用直接 `fetch` 的插件无法取得用户配置的凭据。外部来源与模板来源各有一套轮询实现，投递中断和连续失败的处理也不一致。

## 决策

### 进程与调用

同一个运行时中，每个已启用的插件版本在首次调用时启动一个 worker。工具和来源共享其模块实例。每次调用仍校验批准的代码包哈希。保留一次性 `run()` 入口以及 SDK 根入口的单文件注入方式。插件只导出 `tools`、`sources` 即可继续运行。

插件可以在 `init(ctx)` 中建立连接，在 `close()` 中释放。并发首调共享同一个初始化 Promise。每个调用有独立的 `callId`、期限、取消信号和最多 512 个 Host RPC 的额度，帧上限仍为 4 MiB。worker 用异步调用上下文把 SDK 请求路由到对应的工具或来源，即使插件保存了初始化时的 `ctx`，借用操作也使用当前调用的 broker 和权限。同一次来源拉取期间，同名来源不能重复进入。

取消会立即结束调用方的等待、撤销该调用的 Host RPC。插件可以在其他调用继续运行期间自行返回。如果它一直占用进程，到达原期限后宿主会重置 worker。超时、进程崩溃及 RSS 超限都会清理在飞调用，后续调用按需启动新进程。RSS 由独立线程采样，插件主线程同步阻塞时也能检测。停用、升级、回滚、熔断、设置变更和关闭运行时都会停止对应 worker。宿主发送关闭帧，最多等待 500 ms，再用 SIGKILL 兜底。

### 凭据交付

子进程继续使用环境白名单，剔除与声明密钥同名或含有已知密钥值的变量。`ctx.secrets.list()` 返回本版本清单中的名称。`get(name)` 仅允许读取声明的名称，尚未配置时返回 `undefined`。有效读取及对未声明名称的读取尝试均记入 `audit.jsonl`，只记录插件、密钥名和调用方。

只有 `secrets.get` 对应的成功响应可携带明文凭据。宿主在执行 KV、借用、日志和代理请求前检查参数，在普通 RPC 响应、工具结果、来源数据及错误离开运行时前再次检查。代理额外校验解码后的查询和重定向，仍可按名称在目标请求头中填充密钥。更换配置会释放旧进程和它的模块内缓存。ADR-0016 的用户权限模型继续适用，插件可以主动把读到的凭据传给自己调用的程序或远端。

### 轮询和持久化

外部来源复用 `@alter/plugin-sdk/poller`。首次成功拉取只建立基线。之后保留 1000 个 ID，用 SHA-256 指纹识别顺序未变的溢出段。事件引用继续使用旧格式的 ID 哈希。旧 registry 的 `seen` 和 `next` 会迁移，空的已建基线也会保留。

每次投递确认后，在尝试下一次投递前写入已确认进度。单批前 20 条分别投递，余项沿用一条汇总消息，汇总成功后一起记入进度。今日数统计已确认的来源条目数。投递中途失败或正常停止，下次从未确认的条目继续。事件接收端和 registry 独立提交，如果宿主恰好在事件提交后、断点落盘前崩溃，最后一次投递可能以相同事件引用重试。

每个来源独立保存失败次数、错误、暂停标记和下次拉取时间。第一个暂时性故障等待两个清单间隔，之后按指数退避，最多 64 个间隔。连续三次返回非法数据时，仅暂停该来源并通知用户。工具的连续失败由另一个计数器记录，达到五次才暂停插件。服务端传入应用时区，独立运行时默认使用系统时区并以 UTC 兜底。管理 API 和 SSE 提供上次、下次、今日数、错误和暂停状态，并保留原有的 `next`、`invalid`、`paused`。

## 备选方案

继续使用一次性进程可以避免模块全局状态跨调用，但无法保留长连接。只把原锁改为等待队列，仍会让慢轮询堵住工具。为每个工具或来源启动独立常驻进程可以隔离 CPU 阻塞，代价是重复建立连接、增加常驻内存和初始化次数。

通过环境变量传递凭据会让所有派生程序默认继承它，也无法记录具体哪次调用读取了密钥。Host RPC 保留了这两个控制点。

## 后果

插件作者需要考虑异步工具和来源对模块可变状态的并发访问。等待 I/O 的来源允许工具并发推进，CPU 密集的同步代码仍会占住同一事件循环。每个实际用到的插件版本会占用一个常驻 Node 进程。后续若同步阻塞频繁导致其他调用超时，或实测空闲 RSS 超出部署预算，应重新评估进程数和空闲回收策略。

## 如何验证

在 Apple M1、macOS arm64、Node 24.21.0 上，以同一个已批准的本地工具经 `openRuntime.invoke` 连续调用 20 次。先预热宿主的 SDK 类型剥离缓存。计时包含包哈希检查、RPC 和结果校验，范围从发起调用到取得结果。

| 模式 | 20 次总耗时 | 首次 | P50 | 平均 |
| --- | ---: | ---: | ---: | ---: |
| 一次性 `run()`，20 次冷启动 | 661.33 ms | 31.53 ms | 32.31 ms | 33.07 ms |
| 常驻宿主，1 次冷启动 + 19 次复用 | 38.10 ms | 31.69 ms | 0.33 ms | 1.90 ms |

本次总耗时相差约 17.4 倍。基准随后让来源进入一个由测试控制的未完成借用，确认工具在同一 PID 内返回后才释放来源。该次工具耗时 0.33 ms。测试断言进程复用、调用计数和完成顺序，时延供比较，不作为 CI 门槛。

复现基准：

```sh
pnpm --filter @alter/plugin-runtime exec vitest run test/benchmark.test.ts --reporter=verbose --silent=false
```

回归覆盖超时和崩溃后的重启、阻塞时的 RSS 监控、版本切换与关闭钩子、取消时的 RPC 归属、真实子进程环境与凭据读取、泄露拦截、旧进度迁移、部分投递、来源熔断隔离及 API/SSE 状态。使用 Node 24 执行：

```sh
pnpm -r typecheck &&
  pnpm --filter @alter/plugin-sdk test &&
  pnpm --filter @alter/plugin-runtime test &&
  pnpm --filter @alter/plugin-sources test &&
  pnpm --filter @alter/server test
```
