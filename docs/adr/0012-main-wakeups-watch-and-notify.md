# ADR-0012 主会话何时被唤醒：巡检、盯梢任务与 notify

- 状态：已接受；部分被 ADR-0018 修订
- 日期：2026-11-23
- 修订：ADR-0010 第三条
- 第三次修订：2026-11-23（见文末）

## 背景

主会话是用户唯一的对话对象，它的上下文必须连贯。如果外部消息（每封邮件、每条群消息）都唤醒主会话，上下文会被无关内容冲散，成本也随消息量线性增长。

但完全被动也不行：主会话有时会想关注某件事，例如从对话中得知"老板今晚可能在群里派任务"，需要一种方式让它只在那件事发生时被叫醒。

## 决策

**一、唤醒来源。**

| 会唤醒主会话 | 不会唤醒主会话 |
|---|---|
| 用户在 Web 或飞书机器人发消息 | 新邮件、他人飞书消息（只走分诊，ADR-0010） |
| 任务交报告 | 每日目标调研（结果进摘要） |
| 盯梢任务调用 `finish` | 普通提醒（直接推给用户） |
| 定时巡检 | 每日摘要 |

主会话被唤醒时，输入前缀附带"上次唤醒以来推送给用户的通知"（标题、来源、引用 ID，作为不可信数据）。用户看到通知后说"帮我回一下那封"，主会话能对上号。修订 ADR-0010 第三条：通知不会单独唤醒主会话，只在下一次唤醒时附带。

**二、巡检：按间隔，间隔自适应。**（2026-11-23 修订：原为固定 09:00 / 14:00 / 20:00）

巡检的目的是**主动找事做**，让 Alter 像一个了解用户的人。简报里给主会话的线索**地位相同，没有哪一类优先**：

- 上次巡检以来的摘要级消息汇总（除"立即"之外的通知）
- 目标
- 用户偏好与记忆
- 接下来的日程
- 之前聊天里提到、还没落地的事
- 正在运行的任务（避免重复派单）

提示词明确鼓励主会话**从没列出的地方找事**：根据对用户的了解推测他可能感兴趣的东西。例如判断用户是极客，就找最近的黑客松给他看。不要让巡检变成固定的"处理消息"流程。

主会话对简报全权决定：消息重要就转告用户（`notify`），想干活就派任务或开盯梢，觉得都不重要就什么都不说。什么都不做时不在对话中留痕。

间隔在 2–48 小时之间自动调整，默认 5 小时（只在 08:00–23:00 之间开始巡检）。更短或固定时刻的需求交给定时任务（第六条）：

- **缩短**：近期巡检产出被用户采纳（回复、点"有用"、批准由此派出的任务）；活跃目标多且期限近；用户最近使用频繁；积压的摘要级消息多。
- **拉长**：连续几次巡检的产出用户没有回应或点了"没用"；目标少；用户很久没用。
- 实现：对每次巡检记一个"被采纳"信号，取指数滑动平均作为采纳率，再结合需求量（近期限目标数、积压消息数、用户近 24 小时消息数）算出下一次间隔。初始 5 小时。

采纳率本身是产品指标，进入统计页。**采纳率长期偏低说明巡检做得不好，是要改进的信号**，而不只是把间隔拉长了事。

| 情况 | 处理 |
|---|---|
| 主会话正在处理 | 顺延到空闲，顺延超过 1 小时则跳过本次 |
| 30 分钟内刚活跃过 | 跳过：上下文是新鲜的 |
| 主会话空闲但有任务在跑 | 照常巡检，简报列出运行中的任务，避免重复派单 |
| 上次以来没有新内容 | 跳过，不调用模型 |

**三、盯梢任务（`watch`）。** 主会话的新工具。底层是带触发条件的后台任务，权限、污点、账本规则与普通任务完全相同。

参数：

- 盯哪里：渠道，可细到某个群、某个联系人
- 什么时候：时间段，或从现在起多久
- 关键词：可选
- 任务说明：例如"老板在群里派任务时提醒我"
- 思考强度：默认 low；可用工具与普通任务相同

行为：

- 关键词、群、联系人、时间段的筛选由代码完成，不花 token。命中后才唤醒任务。
- 短时间内的多条消息合并成一批再唤醒（默认 30 秒）。
- 任务每次醒来，判断这批消息是否符合要求：
  - 不符合：调用 `sleep`，继续休眠。专门提供 `sleep` 工具，是为了让"这条不相关"成为一个正当动作，避免模型觉得必须做点什么。
  - 符合：调用 `finish`，报告唤醒主会话。
- 观察期结束时系统再唤醒一次，告诉任务"观察期结束，请收尾"。"总结今晚群聊""把这段时间的邮件附件都下载下来"这类用法依赖这一步。
- 上下文不压缩，任由增长（执行模型便宜）。
- 被盯的消息是外部数据，任务读到即带污点；交给主会话的报告也按任务数据处理。

消息怎么到达：

- 飞书只会实时推送机器人能收到的消息（机器人私聊、有机器人的群里 @ 它的消息）。这类消息走实时触发。
- 没有机器人的群、他人发给用户本人的消息，用用户身份定时拉取，默认每 1 分钟一次。
- 邮件同样定时拉取。

**四、`notify` 工具。** 主会话被非用户来源唤醒（任务报告、盯梢、巡检）时，它的回复**默认只写进 Web 时间线，不推送**。值得告诉用户时，主会话调用 `notify(级别, 内容)`，由通知中心按渠道推送。安静时段规则同样适用（深夜"立即"降为摘要）。用户主动发消息时，回复照常回到原渠道。

**五、分诊与盯梢的分工。**

- 分诊管"这条消息要不要打扰用户"，面向用户，对所有外部消息兜底运行。
- 盯梢管"主会话自己想知道的事"，面向主会话，只在主会话开启时运行。
- 去重：同一条消息既触发盯梢、又被分诊判为"立即"时，分诊不再单独推送，由主会话决定如何告知。

**六、定时任务。** 主会话的工具 `schedule_task`，到点派一个普通任务（权限与审批规则不变），或唤醒主会话。触发方式：

- 某个时间点一次
- 固定间隔（例如每 30 分钟）
- 每天 / 每周固定时刻
- 绑定日程：日程开始前或结束后多久（日程改期时跟着变，删除时取消）

可以指定 `continue_from` 接续某个任务的对话。定时任务在 Web 上可查看、暂停、删除；计入每日主动预算。

## 备选方案

- **每条外部消息都唤醒主会话**：上下文被冲散、成本线性增长，否决。
- **盯梢用分诊的临时规则实现**：更省，但只能打标签，做不了"总结群聊""下载附件"这类事，也无法跨多条消息判断。否决，改为任务形态。
- **常驻巡检任务代替主会话巡检**：巡检的目的正是让主会话主动规划，交给任务就失去了这一点。

## 后果

- 正面：主会话上下文只包含与用户相关的事；主动性由主会话自己决定，开销可控。
- 负面：盯梢任务在热闹的群里会频繁醒来；用合并唤醒和关键词缓解，并计入每日主动预算。

## 第三次修订（2026-11-23）：外部信号都交给主会话判断

原则：**分诊和调度只负责过滤和计时，不替主会话做决定。** 主会话是唯一判断"告诉用户、派任务，还是什么都不做"的地方。

**一、分诊判为 now 的消息唤醒主会话，不再直接推送给用户。** 重要消息的意义不只是让用户看到，而是让主会话判断要不要通知、要不要派任务去处理。消息作为不可信数据附在唤醒输入里。安静时段照常唤醒主会话，但 `notify` 的"立即"仍按安静时段降级。第五条的去重随之简化：盯梢命中的消息交给盯梢任务，不再重复唤醒。

**二、取消固定 21:00 每日摘要，改为按使用频率发的"近况报告"。** 到期时唤醒主会话，由它整理后发出，内容包括：

1. 这段时间的消息摘要（digest 级）；
2. 完成了哪些任务；
3. 其中哪些是 Alter 主动做的（巡检、定时任务、盯梢发起），以及结果；
4. 末尾 1–2 道反馈题（与每周回访共用题库，见 ADR-0017）。

频率随使用情况调整：最近天天在用，每天发；用得少，隔 2–3 天发；近期几乎不用就不发。没有值得说的内容时跳过本次。

**三、用户长期不用时全面安静。** 连续 7 天没有任何用户互动时，暂停巡检和近况报告，只保留"重要消息唤醒主会话"。用户回来后恢复，并把这段时间的情况合成一份近况报告。主动式 Agent 最忌讳的是用户走了，它还在自己忙。

**四、定时任务分两种，工具改为 create / list / set。**

- `schedule_create`：类型三选一，分别是**提醒**（到点直接通知用户）、**派任务**（到点直接派出任务，不经过主会话；任务报告照常唤醒主会话）、**唤醒主会话**（需要主会话综合判断的安排）。
- `schedule_list`：查看全部。
- `schedule_set`：修改时间或内容、暂停、恢复、删除。新建的语义比较独立，单独做一个工具，免得模型把新建和修改搞混。

**五、任务工具：`task_cancel` 改名为 `task_stop`。** 语义是暂时中断，之后仍可用 `continue_from` 接续。盯梢工具保持独立，不并入任务工具。

**六、删除两条旁路。**

- **审批超时唤醒**：审批到期后任务会被拒绝并提交报告，主会话从报告中得知，不再单独唤醒。审批机制本身之后另行讨论。
- **目标复查**（M4 #48）：它早于巡检设计，由调度器绕过主会话直接派调研任务，与"线索平权、主会话决定"相冲突。目标本来就是巡检的线索之一，删除后由巡检接手。

**七、主会话可以租用几乎所有工具。** 一两步就能完成、结果不长的事，主会话自己做；需要翻多个网页、结果很长或运行很久的事，派任务。理由：浏览器一次快照就有几千 token，会撑大主会话的上下文，也会降低提示缓存命中率。前提是主会话同样受污点约束：读过外部内容后，对外发送要审批，直到这些内容被上下文压缩移出为止（具体规则与上下文压缩一起讨论）。每次租用都要写理由，并计入统计，用来比较"自己做"和"派任务"的效果。

#95 实施口径：已启用插件的所有动作可按能力或单个 action 租用，含旧清单的工具。记忆、调度及主会话控制工具常驻；任务的 finish、declare_permissions 和盯梢 sleep 依赖子任务身份，不进入租约。空能力和纯消息来源没有可租动作。

带污点时，只读租约直接发放，含写入、发送、不可逆或未知动作的租约由 Broker 向用户申请。执行时重新按具体参数审批；从干净会话取得的写租约同样受之后新增的污点约束。经用户同意的租约理由可供审批模型核对具体调用，主会话仍只接受用户的单次决定。现有压缩摘要可能转述外部内容，压缩本身不会清除污点。

修订后唤醒主会话的来源：用户消息、任务报告（包括盯梢收尾、定时派出的任务）、分诊判为 now 的消息、巡检、"唤醒主会话"类定时任务、近况报告到期。

## 修订：巡检先探索，再由主会话决定行动（2026-11-25）

原始线索直接交给主会话时，模型经常把用户已经知道的事情重述一遍。现在，巡检通过原有的时段、忙闲、指纹和预算检查后，先派一个携带主会话上下文的探索任务。网页任务列表显示「巡检探索」和派发时间。探索调用计入主动预算，启动时预算不足就跳过整次巡检。

探索任务收到六类原始线索与最近三次巡检的结论摘要，均按不可信数据处理。它可从用户提过的来源或已启用的插件中寻找新进展，核对用户是否已知，并在结论中写明理由和建议动作。结论随巡检记录保存，供后续探索去重。

探索成功后，主会话只收到一次巡检唤醒，依据探索报告决定行动。探索报告跳过普通任务报告唤醒。探索失败、取消或超过十分钟时，巡检记录保存原因，主会话改用派发时的六类线索。能先做的事就先派任务，完成后再告诉用户；只有新信息或已经完成的工作值得告知。什么都不做也是正当结果。
