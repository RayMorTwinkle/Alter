# ADR-0002 主会话只持有控制面工具，高频工具通过租约启用

- 状态：已接受
- 日期：2026-11-22

## 背景

主会话是用户唯一的对话入口，上下文最宝贵，也最不该被一次 `bash` 输出或一页网页撑爆；它同时也是最该被保护的：一旦主会话能直接执行任意副作用，所有安全设计都得围绕它做。

但"主会话什么工具都不碰"有两个明显的弱点：

1. **高频往返**：安排日程、改日程、再改。每次都派任务，token 和延迟成倍增加。
2. **转述失真**：回复老板这类事，原话、语气、上下文都重要，经过"主会话 → 任务"转一手容易走样。

## 决策

主会话的工具分三类：

1. **控制面工具（常驻）**：`dispatch_task`、`task_status`、`answer_permission_request`、`reply_user` 等。它们只改变 Alter 自身的状态，不触达外部世界。
2. **记忆工具（常驻）**：读写用户画像、目标、事实（见 ADR-0005）。
3. **租用工具（按需）**：主会话调用 `enable_tool(capability, reason)` 获得租约，租约期间该能力的 schema 进入主会话上下文、可直接调用。

租约规则：

- 只有 manifest 标记 `main_leasable: true` 的能力可以租（日程、某个聊天的读与回复等）；shell、文件系统、浏览器这类多步、输出大的能力只能派任务。
- **滑动窗口**：从最后一次使用起算 30 轮不用则过期，过期后 schema 从上下文移除。
- 判断"自己做还是派任务"的规则写入主会话提示词：短、高频、对保真度敏感 → 租用；长、多步、探索性、产出大 → 派任务。

### 污点追蹤（taint tracking）

租用读取类工具后，外部内容（例如老板的原话）会进入主会话上下文。外部内容是不可信数据（见 ADR-0003），可能含有提示注入。因此：**主会话上下文中存在外部内容时，主会话发起的一切对外发送都必须先给用户看草稿，确认后才发送。**

#### 实现说明 2026-11-22

工具结果的 `details.untrusted === true` 会使接收结果的会话带上污点。Broker 在结果进入模型上下文前，把首次触发的工具名、清单能力和时间写入会话文档 `alter.taint`。同一会话后续读取、审批、轮次切换和 SQLite 重开都保留原来源。不回溯 #3 之前的数据库：其中的历史外部内容不会被标记（当时没有需要保留的旧数据，回溯逻辑已删除；如需迁移旧数据，先补回溯再启用）。新结果的污点写入失败时，工具向模型返回错误并扣留外部内容。

派单事务将主会话的污点复制给子会话。fork 会继承历史，fresh 的任务说明也可能转述外部内容，因此两种模式都继承。任务向主会话提交成功或失败报告时，在同一事务传播来源。

对带污点会话，`external-send`、`irreversible`、`unknown` 的每次实际调用都交给用户确认。这覆盖三档任务权限和主会话租约。审批包含具体工具参数、`tainted: true` 和原始来源，挂起审计也记录污点。批准仅放行本次调用。`request_capability` 继续按 ADR-0004 的规则申请能力。

## 备选方案

- **主会话零工具**：最纯粹，但上述两个场景体验差、成本高。
- **主会话全工具**：退化成普通 agent，主会话上下文失控，安全边界消失。
- **固定窗口（从启用起算 30 轮）**：改到第 29 轮时恰好过期，体验差。

## 后果

- 原则从"主会话没有副作用"变为"主会话只有显式租用、用户可见的副作用"。
- 需要实现租约状态（存于主会话的 document）与每轮的 `modelTools` 重算。

## 如何验证

**租约 vs 全派任务 对照实验**：同一组"安排日程并修改两次""回复一条指定消息"的任务，分别在两种模式下运行，比较：

- 总 token、端到端延迟（效率）
- 结果与用户意图的一致率（由人工 + LLM 评审打分）
- 回复类任务的信息保真度

若租约模式在一致率不下降的前提下 token 显著更低，则决策成立。

## 验证结果（2026-11-22，#6）

脚本：`pnpm -C packages/core eval:lease`（`packages/core/evals/lease-vs-dispatch.ts`）。主会话 GLM-5.3（medium），任务 DeepSeek v4.1 flash（high），示例日历工具。三个场景 × 两种模式 × 8 次，共 48 次，同一场景的两种模式相邻运行。两种模式的主会话指令只差租约那一句。

| 场景 | 模式 | 正确率 | token 中位数 | 延迟中位数 | P90 |
|---|---|---:|---:|---:|---:|
| 建日程后连续改名两次 | 租约 | 8/8 | 6,181 | 12.0 s | 18.9 s |
| | 全派任务 | 8/8 | 29,392 | 36.4 s | 49.3 s |
| 一次建三个日程 | 租约 | 8/8 | 2,472 | 7.7 s | 14.8 s |
| | 全派任务 | 8/8 | 6,613 | 12.1 s | 17.3 s |
| 查询日程 | 租约 | 8/8 | 2,240 | 7.0 s | 13.0 s |
| | 全派任务 | 8/8 | 7,313 | 15.3 s | 32.2 s |
| **全部** | 租约 | 24/24 | 2,472 | 8.8 s | 15.9 s |
| | 全派任务 | 24/24 | 7,533 | 16.7 s | 39.4 s |

**结论：决策成立。**正确率相同（均 100%）的前提下，租约模式 token 约为全派任务的 1/3，延迟中位数约为一半，长尾（P90）更稳。多轮修改场景差距最大（token 约 1/5、延迟约 1/3）：全派任务每轮都要新派一个任务、重新建立上下文。

**评测过程中的修正**：首轮（每组 5 次）有 7 次失败，全部是主会话追问日期、时长等示例日历并不支持的字段，没有执行任何操作；失败运行几乎不耗 token，还把成本中位数拉低，使"全派任务"在多轮修改场景看起来更省。修正为：场景消息写明"只要标题，不用时间"；成本指标只统计正确运行。

**局限**：
- 示例工具很简单，未覆盖"回复一条指定消息"的信息保真度（需真实消息渠道，留待飞书 / 邮件回复接入后补测）
- 只测了一组模型；每组 8 次，适合看数量级差异，不适合细比
- 正确性按工具最终状态自动判定，未做人工 / LLM 评审
