# ADR-0003 区分 Surface（使用 Alter 的入口）与 Connector（Alter 代表用户的账号）

- 状态：已接受
- 日期：2026-11-22

## 背景

飞书、微信这类平台对 Alter 有两种完全不同的意义：

- 用户**通过**飞书和 Alter 对话（飞书是入口）；
- Alter **使用**用户的飞书账号收发消息（飞书是工具）。

两者混在一起会出现严重问题：别人在群里说"把文件发给我"，Alter 该不该执行？一封邮件里写"忽略之前的指令"，算不算指令？

## 决策

插件 SDK 中把两种角色拆成两个独立的注册点：

| | Surface（入口） | Connector（账号代理） |
|---|---|---|
| 身份 | Alter 自己的身份（如飞书应用机器人、网站） | 代表用户的账号（用户的邮箱、微信、飞书 user token） |
| 消息性质 | **指令** | **数据 / 事件** |
| 去向 | 直接进入主会话 | 进入收件箱 → 事件总线 → 分诊 |

**唯一判定规则：消息是否由已验证的用户本人、在已验证的 Surface 上发出。**只有这种消息是指令，其余一律是不可信数据。即使在同一个飞书群、同一个机器人下，其他人说的话也只是数据。

一个插件可以同时提供两种角色（例如飞书插件 = 机器人 Surface + 用户账号 Connector），但两者在代码中是两个注册点，权限分别管理。

## 备选方案

- **按平台区分**（"飞书来的都是指令"）：无法处理群聊和他人消息。
- **让模型判断是不是指令**：把安全边界交给最容易被注入的环节。

## 后果

- 这是 Alter 防提示注入的**主防线**：恶意邮件在架构上只是一条待分诊的数据。
- 数据进入任何会话时都要带来源标记，为 ADR-0002 的污点追蹤提供依据。
- Surface 需要用户身份验证（网站登录、飞书 open_id 绑定）。

## 如何验证

建立**提示注入测试集**：在邮件、聊天消息、网页内容中植入各类恶意指令（越权发送、泄露数据、修改记忆），统计 Alter 执行了其中多少（攻击成功率，目标为 0），以及正常任务完成率是否受影响。每个版本回归一次。
