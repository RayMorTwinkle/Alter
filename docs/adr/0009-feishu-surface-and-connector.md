# ADR-0009 飞书：机器人 Surface 与用户账号 Connector 分开接入

- 状态：已接受；部分被 ADR-0018 修订
- 日期：2026-11-22

## 背景

飞书是 Web 之后的第二个入口，也是 ADR-0003 那条规则第一次真正受考验的地方：同一个飞书里，用户本人发给机器人的话是指令，群里其他人的话、用户账号收到的消息都只是数据。

约束：

- Alter 跑在用户自己的电脑上，没有公网地址，收不到 HTTP 回调。
- 审批要能在手机上完成，否则离开电脑后任务会一直卡在等待审批。
- 用户身份必须由系统确认，不能靠模型从消息内容判断"这是不是主人"。

## 决策

**一、两个角色是两个注册点。**

| | 机器人 Surface | 用户账号 Connector |
|---|---|---|
| 身份 | 飞书自建应用的机器人 | 用户本人（user_access_token） |
| 注册点 | `AlterSurface`：拿到 `AlterApp`，和 Web 服务器同级 | `AlterPlugin`：能力清单 + 工具，经 Broker 授权 |
| 进入主会话的内容 | 主人私聊机器人的文字（指令） | 工具结果（数据，带污点） |
| 其他人的消息 | 机器人收到的群聊 @、陌生人私聊 → 外部事件（不可信） | 全部是数据 |

**二、长连接收事件。** 用飞书官方 SDK 的 WebSocket 长连接订阅 `im.message.receive_v1` 和卡片回调，不需要公网地址。

**三、主人身份靠配对码绑定。** 未绑定时，服务启动日志和 Web 界面显示一次性 6 位配对码（10 分钟有效）；在飞书私聊机器人发送这个码，就把发送者的 open_id 记为主人，写入数据目录。之后只有"主人 open_id + 私聊会话"的消息算指令。配对码只证明"这个飞书账号的主人也能看到 Alter 的本机界面"，所以看不到界面的人无法绑定。

**四、回复回到发起的入口。** 用户输入记录来源（`web` / `feishu`）。主会话对飞书来的输入的最终回复发回飞书私聊；Web 发起的对话不推到飞书，避免两边重复。任务报告和主动通知（M4）的去向以后由通知分级决定。

**五、审批卡片。** 待审批的请求在飞书私聊里发一张卡片（工具、参数摘要、批准 / 拒绝）。卡片回调只接受主人 open_id；Web 和飞书谁先答以谁为准，另一边随之更新为已处理。

**六、用户账号 Connector 用 OAuth。** 在 Web 设置页点"连接飞书账号"，走授权码流程，回调地址是本机 Web 服务；令牌存数据目录（权限 0600），自动刷新。工具按副作用分级：读会话和消息是 `read`，以用户身份发消息是 `external-send`。消息内容一律带污点，所以读过别人消息之后的发送都要用户批准（ADR-0002 污点规则）。

## 备选方案

- **HTTP 事件回调**：需要公网地址或内网穿透，多一个暴露面，放弃。
- **配置文件里手填主人 open_id**：用户要先去开放平台查 open_id，而且填错了没有任何提示；配对码一步完成，还能顺便验证机器人能收能发。
- **飞书一切消息都进主会话，让模型分辨谁是主人**：等于把安全边界交给最容易被注入的环节（ADR-0003 已否决）。
- **用机器人身份读群消息代替用户 token**：机器人只能看到它所在的群，覆盖不了用户真正关心的会话；而且会把"Alter 的身份"和"用户的身份"再次混在一起。

## 后果

- 主会话第一次有两个入口，用户输入要带来源，时间线要能显示来源。
- 机器人 Surface 不经过 Broker：它不是能力，而是一个和 Web 一样的人机界面。能做什么仍由主会话和 Broker 决定。
- 用户需要在飞书开放平台创建一个自建应用，并开通权限、发布版本，这一步只能由用户完成。
- 卡片审批让离开电脑时也能放行任务，审批超时（#4）在实际使用中会少触发。

## 如何验证

- 离线：假飞书服务器上测配对、非主人消息只进事件列表、群聊消息不触发主会话、卡片回调拒绝非主人。
- 提示注入测试集（M3 验收）：在邮件、网页、飞书消息里植入越权指令，统计执行成功的攻击数，目标为 0；同时统计"智能体提出了攻击要求的操作、被审批拦下"的次数，它代表用户被打扰的代价。
- 真实环境：手机飞书完成一次 对话 → 派任务 → 卡片审批 → 收到回复。
