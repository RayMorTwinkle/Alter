# 主模型对比：GLM-5.3 与 GPT-6.2-sol（#10，简化版）

- 日期：2026-11-22
- 任务集：端到端评测 11 条任务（[基线报告](2026-11-22-e2e.md)）
- 设置：只换主会话模型（`ALTER_MAIN_MODEL=codex/gpt-6.2-sol`，不带回退链），任务模型不变（DeepSeek v4.1 flash）；每条 2 次，共 22 次
- 范围：用户决定只做 sol 的简单对比，GPT-6.2-astra 不测

## 结果

| | GLM-5.3（基线，33 次） | GPT-6.2-sol（22 次） |
|---|---:|---:|
| 完成率 | 33 / 33 | 21 / 22 → 判定修正后 22 / 22 |
| 主会话调用次数中位数 | 4 | 11 |
| 主会话输出 token 中位数 | 264 | 413 |
| 延迟中位数（总计） | 13.3 s | 32.6 s |
| 延迟中位数（浏览器） | 14.7 s | 62.4 s |
| 每次运行平均派任务数 | 0.58 | 0.73 |

唯一的失败是 `calendar-conflict`：sol 回答「『星图交流会』从下午 3 点开到 4 点」，内容正确，但判定只认「15:00」。判定已改为同时接受「下午 3 点」，属于评测问题而不是模型问题。

## 不能直接比的数字

主会话输入 token 相差约 5 倍（同一条日历任务，同样 3 次调用：GLM 3,444，sol 18,672）。记录口径已经包含缓存读写，差距来自网关两侧：`codex/` 通道会在请求前加上自己的系统指令，输入 token 不代表 Alter 自己的提示长度。因此 token 不用于跨通道比较成本；`codex/` 通道走订阅，按次计费的边际成本也无法从 token 推算。

## 结论

- 当前任务集上两者完成率没有差别，任务逻辑还不复杂，GLM-5.3 足够。
- sol 主会话调用次数约为 GLM 的 3 倍，延迟约 2.5 倍（浏览器任务约 4 倍），交互体验明显更慢。
- 维持 GLM-5.3 为主模型、sol 留在回退链里。等 M4 的分诊、目标驱动等更难的判断上线后，再用新的任务集重比（包括 astra）。

## 局限

- 每条任务只跑 2 次，只能发现大的差别。
- 没有逐条核实 sol 多出来的主会话调用具体花在哪里（推测是等待任务时的额外轮次）。
