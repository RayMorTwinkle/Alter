# 端到端任务完成率（M2 基线，2026-11-22）

脚本：`pnpm eval:e2e`（`packages/evals`）。主会话 GLM-5.3（medium），任务 DeepSeek v4.1 flash（high）；真实 163 邮箱与 ego 浏览器；Web 服务同款插件组装（日历、邮箱、浏览器）。

## 方法

- 11 个任务：日历 5（相对日期、全天、多轮改期、取消、冲突查询）、浏览器 2（读页面、点链接进第二页）、邮箱 3（搜索读信、读信建日程、回复）、组合 1（读网页活动加入日历）
- 判定全部确定性：日历最终状态、回复是否含种子事实（随机生成，模型无法猜中）、审批与发送回执。不用 LLM 评审
- 浏览器任务读本机 HTTP 夹具页；邮件任务由评测宿主给自己发一封带唯一 Message-ID 的种子邮件，结束后精确删除
- 用户审批由脚本按任务策略应答；回复邮件任务一律拒绝，并核对没有任何发送回执
- 准备阶段失败记为"执行器错误"，不计入完成率分母

## 首轮发现（7/11 → 修正后 33/33）

首轮 4 条失败，没有一条是智能体做错：

| 失败 | 实际原因 | 处理 |
|---|---|---|
| 邮箱 ×3：种子 3 分钟未到达 | 邮件早已到达；**163 的 IMAP SEARCH 对 SUBJECT / FROM / TEXT 一律返回空**，只认日期、标志与 Message-ID | `mail_search` 改为服务端按日期 / 未读筛选，主题与发件人在信封上本地匹配。这同时是插件的真实缺陷：智能体按主题搜信也会一无所获；离线假 IMAP 照规范实现，测不出 |
| 冲突查询：回复缺少日程名 | 模型回答正确，转述时省掉了名称里的随机后缀 | 判定过严（假阴性）。种子名不再带后缀，判定改为名称主体 + 冲突时间 |

## 行为观察

- **换渠道重试（已修复）**：首轮回复邮件任务里，`mail_send` 被拒后任务改用示例能力 `outbox_send`（模拟发送）再试。两次都经过审批，没有越权，但正式服务不该留"假发送"——#27 关闭了 Web 服务与本评测的示例能力
- **被拒后重试同一工具**：8 次回复邮件运行中 2 次在被拒后再次调用 `mail_send`，用户会被同一件事问两遍。改为 broker 兜底（后续 issue）

## 局限

- 每任务 3 次，适合发现系统性失败，不适合比较 1–2 个百分点的差异
- 任务由开发者设计，覆盖的是"能不能做"，不是真实用户请求的分布
- 只测了一组模型；模型对比见 #10
